# 双击亮屏 / 抬腕亮屏 不可用 —— 根因分析

- 机型：Xiaomi 15（`ro.product.device=dada` / 24129PN74C / sn `9dea5b0e`，SDK 36 / Android 16）
- ROM：Flyme 12.6.0.0A，`ro.product.flyme.model=M2582`（= 魅族 20 Pro 的 system / system_ext / product）+ 小米 HyperOS 的 vendor / odm（odm 来自 C17 底包）
- 分析样本（全部可在本机复现，无需真机）：
  - 移植包 `MIO-KITCHEN-4.2.1-win\flyme\`（只读）
  - `_sysui\framework-res.apk` = 移植包 `system\system\framework\framework-res.apk`（md5 `0E6E9739FB7A8D12086BFB9B08DB720A`）
  - `_settings_apk\Settings.apk` = 移植包 `system_ext\priv-app\Settings\Settings.apk`（md5 双方一致 `8ADCA90CC6FF3E15963EC358A024FE66`）
  - `system_ext\apex\com.flyme.runtime.apex` → 内含 `com.android.server.policy.gesture.**`（**手势服务不在 services.jar 里**）
  - `product\overlay\FrameworksResCommon_Sys.apk`（魅族 RRO）、`vendor\lib64\vendor.xiaomi.hw.touchfeature-V1-ndk.so`
  - 真机 logcat：`ui.txt`、`live2.log`、`live3.log`、`live_unlock.log`

## 0. 结论速览

| 功能 | 设置项 | 实际实现（唯一的） | 断点 | 硬证据 |
|---|---|---|---|---|
| 双击亮屏 | `mz_quick_wakeup_double_click` | system_server `GestureManagerService` 把位图写进 **`/sys/class/meizu/tp/gesture_control`**（MARS 机型另走 `goodix_ts.0`） | 该魅族节点在本机不存在 → 写入 100% 失败，触摸 IC 从未进入手势/双击模式 | `NoSuchFileException: /sys/class/meizu/main_tp/sleep`、`Unable to write .../screen_mode_node`、`onDisplayChanged,isGestureEnabled:false` |
| 抬腕 / 翻转亮屏 | `raisewakeup_switch` / `flipwakeup_switch` | SystemUI `RaiseFlipperController`，传感器 = **魅族私有类型 65538 / 65539** | 本机没有这两个传感器（小米 vendor + 魅族 HAL 缺失）→ 连设置开关都被判为"设备不支持"而隐藏 | `config_flipSensorType=65538`、`config_raiseSensorType=65539`，`supportRaiseFlipFeature()` 两个 `getDefaultSensor()` 都为 null；`vendor.meizu.sensor_aux.ISensorAux` 未实现 |

> 上面是**设备离线时**的静态分析结论（事后看仍然成立）。真机接入后的复测、修复过程与三次更正（开关不联动、
> 开机 power 服务竞态、以及"fabricated overlay 重启不丢"这个**错误结论**的更正）都在 8.x / 9 / 10 节。
> 想"一页看完"就看同目录 [`双击亮屏与抬腕亮屏-总整理.md`](双击亮屏与抬腕亮屏-总整理.md)。

**共同根因**：这一版移植是"魅族 Flyme 的 system 层 + 小米的 vendor/odm"。双击/手势亮屏与抬手亮屏**都只由魅族私有硬件接口（魅族触摸屏 sysfs 节点、魅族私有传感器类型 + SensorAux HAL）驱动**，而这两套接口在这台机器上根本不存在；移植只桥接了**指纹（FOD）**那一条（porter 自建 `mifod/fod-bridge.jar` → 小米 `ITouchFeature`），触摸手势通道和抬手传感器通道都没有桥接。

## 1. 双击亮屏

### 1.1 开关是可见的（问题不在"没有选项"）

- 显示页：`_settings_jadx\resources\res\xml\mz_display_settings.xml:92-96`，`quick_wakeup_double_click` → `FlymeDoubleClickWakeUpController`
- AOD 与锁屏页：`aod_and_lockscreen_settings.xml:57-60` 同一个 key（由 `AODAndLockScreenSettings.java:313-314` 直接写值）
- 控制器用 `android:bool/config_automatic_brightness_available`（`0x1110042`）判可见性，见 `_settings_smali\...\FlymeDoubleClickWakeUpController.smali:24-53`
- framework-res 里该 bool = **false**，**但**魅族自己的 RRO `product\overlay\FrameworksResCommon_Sys.apk`（`package=android.overlay.common`、`targetPackage=android`、`isStatic=true`、`priority=100`）把它覆写为 **true** → 真机上开关**可见、默认显示为开**

### 1.2 开关只写了一个 Settings 值，真正的开关在 system_server

- `FlymeDoubleClickWakeUpController.setChecked()` → 写 `Settings.System.mz_quick_wakeup_double_click`，随后调用 `FlymeQuickWakeupFragment.updateQuickWakeupSwitchValue()` 计算总开关 `mz_quick_wakeup_switch`（所有手势项都为 0 才写 0）
- 但 system_server 侧读的是默认 0：`GestureManagerService.getMainScreenGestureControl()` 用 `Settings.System.getInt(cr, key, 0)`（`GestureManagerService.java:329-337`）
- ⇒ **显示与实现不一致**：全新刷机/清数据后 UI 显示"双击亮屏 = 开"（读默认 1），系统却按 0 处理。日志里 `isGestureEnabled:false` 正是这个状态

### 1.3 唯一的触摸屏控制通道是魅族 sysfs，本机不存在（核心断点）

`GestureManagerService` 的节点路径不是硬编码，而是取自 framework-res 字符串资源：

```
android:string/gesture_control_path_string (0x01040bcd) = /sys/class/meizu/tp/gesture_control
android:string/touch_panel_sleep_path       (0x01040d72) = /sys/class/meizu/main_tp/sleep
```

位图映射（`GestureManagerService.java:151-167` `initURLKeyMap()`）：

```
mz_quick_wakeup_double_click -> 0x00000010 (DOUBLE_TAP_ENABLE)
mz_quick_wakeup_slide_up/down/left_right -> 4 / 8 / 3
mz_quick_wakeup_draw_c/e/m/o/s/v/w/z   -> 256/128/1024/2048/4096/8192/512/16384
mz_quick_wakeup_once_tap               -> 0x00000020
mz_quick_wakeup_switch                 -> 0x80000000 (ALL_GESTURE_ENABLE)
mz_fingerprint_enable                  -> 0x01000000 (FOD_ENABLE)
```

下发方式：`setMainGestureControlValue()`（`:340-349`）→ `writePath(mMainGestureControlPath, intToByteArray(value))`（4 字节小端，`:259-314`）；`writePath` 遇到 `NoSuchFileException` **只打日志后 return**，不抛异常、不影响开机。熄屏/亮屏时再写 `/sys/class/meizu/main_tp/sleep`（`writeTouchPanelSleepNode() :364-370` → `writeNode() :373-402`）。

真机日志（三份 logcat 表现完全一致）：

```
E SystemGesture-GestureManager: Unable to write /sys/class/meizu/main_tp/sleep/sys/class/meizu/main_tp/sleep   (live_unlock.log:4564, live3.log:2668)
    java.nio.file.NoSuchFileException: /sys/class/meizu/main_tp/sleep
      at com.android.server.policy.gesture.GestureManagerService.writeNode(GestureManagerService.java:442)
      at ...writeTouchPanelSleepNode(GestureManagerService.java:436)
      at GestureManagerService$2.onSensorChanged(GestureManagerService.java:139)
E SystemGesture-SystemGesture: Unable to write /sys/class/meizu/main_tp/screen_mode_node        (ui.txt:4507 等)
I SystemGesture-GestureManager: onDisplayChanged,isGestureEnabled:false,isFodEnabled:true      (live2.log:7157 等，共 200+ 次)
```

`onDisplayChanged` 里 `isGestureEnabled = (mMainGestureControl & 0x80000000) != 0`（`:83-92`）——**从头到尾都是 false**，即触摸 IC 从未收到"开启手势"的指令。IC 不在手势模式，双击时它什么都不会上报，所以怎么点都不会亮。同理，画字母/上滑/下滑等"手势唤醒"也全部不可用。

### 1.4 另一条魅族通道（MARS 机型）在本机也不生效

`FlymeTPController` 走的是汇顶 Goodix 节点（`/sys/devices/platform/goodix_ts.0/double_en`、`gesture_c/up/down/left/right`、`prevent_gesture` 等），但它的启用条件是 `BuildExt.IS_MARS`（`_fx\jadx3\sources\android\os\BuildExt.java:125`：`ro.product.flyme.model == "mars" || "M2392"`）。本机 `ro.product.flyme.model=M2582` → **IS_MARS=false，这条路径压根没被初始化**（且 dada 上也没有 goodix 节点）。

### 1.5 输入层：即使产生事件，也要看设备名和 .kl

- 本机触摸输入设备名是 **`Xiaomi_Touch_Input_0`**（`live3.log:241` `Device reconfigured: id=8, name='Xiaomi_Touch_Input_0'`）
- 移植包里魅族手势扫描码只存在于魅族自己的键盘映射里：
  `system\system\usr\keylayout\fts.kl` 与 `main_touch.kl`（两者 md5 均为 `0B4A94752C70F41708AC91ED466AC6D1`）含 `key 624 DOUBLE_TAP`、625、626、640-666
- **全树没有任何 `Xiaomi_Touch_Input_0.kl`** → 该设备回落 `Generic.kl`，而 `Generic.kl` 含 `key 143 WAKEUP`
- 框架侧确实认识魅族键名：`framework.jar classes4.dex` 内含 Flyme 自己补的标签（`ONECE_TAP`、`SWIPE_X_LEFT`）

⇒ 若小米驱动在手势模式下上报 **143**，`Generic.kl` 会当 **WAKEUP** 唤醒屏幕（这正是 MIX4 那台"只补 keylayout 就修好"的原因）；若它上报 **624+**，则因设备名不匹配魅族 .kl 而变成 UNKNOWN。**这一点必须真机确认**（见第 4 节）。

## 2. 抬腕 / 翻转亮屏

### 2.1 开关被直接隐藏（所以设置里根本找不到）

`MzUtils.supportRaiseFlipFeature()`（`_settings_jadx\...\utils\MzUtils.java:837`，smali `_settings_smali\...\MzUtils.smali:7145-7204`）逻辑：

```java
int flip = res.getInteger(res.getIdentifier("config_flipSensorType", "integer", "android"));
int raise = res.getInteger(res.getIdentifier("config_raiseSensorType", "integer", "android"));
return sensorManager.getDefaultSensor(flip, true) != null
    && sensorManager.getDefaultSensor(raise, true) != null;   // 两个都必须存在
```

framework-res 的实际值（魅族私有类型，AOSP 未定义）：

```
integer/config_flipSensorType  (0x010e01db) = 65538
integer/config_raiseSensorType (0x010e01f3) = 65539
```

全树 RRO 扫描（所有 `resources.arsc` 里含这些名字的 apk）结果：**只有 framework-res 自己与那份魅族 RRO，没有任何 overlay 覆写这两个整数**（RRO 只覆写了 `config_automatic_brightness_available`）。小米 15 的 sensor HAL（Qualcomm SSC + 小米 dynamic/touch-detect，`vendor\etc\sensors` 与底包逐字节相同）不可能提供 65538/65539 → 两个 `getDefaultSensor()` 都是 null → 返回 false。

两个入口因此都把开关拿掉：

- 显示页：`FlymeRaiseFlipController.getAvailabilityStatus()` = `MzUtils.supportRaiseFlipFeature(ctx)` → 返回 `3`（UNSUPPORTED_ON_DEVICE，Settings 框架自动隐藏）
- AOD 与锁屏页：`AODAndLockScreenSettings.java:160-162` → `getPreferenceScreen().removePreference(this.mRaiseFlip)`

### 2.2 就算强行写值也不会亮：实现是 SystemUI 的 RaiseFlipperController

`_sysui\jadx_out\sources\com\flyme\keyguard\RaiseFlipperController.java`：

```java
:207-210  mFlipSensor  = sm.getDefaultSensor(config_flipSensorType /*65538*/, true);
           mRaiseSensor = sm.getDefaultSensor(config_raiseSensorType/*65539*/, true);   // 本机两者皆 null
:225-242  updateRaiseAndFlipSensor(on) → sm.registerListener(listener, mFlipSensor/mRaiseSensor, 3)
           // sensor == null 时 registerListener 直接返回 false，不抛异常 → 静默失效
:245-248  updateTriggerRaiseSensor() → if (mRaiseSensor == null) { log "return for null raise sensor"; return; }
:196      mRaiseWakeupOn = Settings.System.getIntForUser(cr, "raisewakeup_switch", 0, -2) == 1;
:198      ContentObserver 监听 raisewakeup_switch / flipwakeup_switch
```

唤醒动作本身是现成的：抬腕（`values[0]==2`）→ `mHandler.sendMessage(1001)` → `mPowerManager.wakeUp(SystemClock.uptimeMillis(), "systemui raise_wakeup")`；翻转 → `flip_wakeup`；放下（4/5/7）→ 再息屏。

⇒ 与 MIX4 报告的结论相同：**`settings put system raisewakeup_switch 1` 也不会有任何效果**，因为传感器对象是 null（日志里连 `RaiseFlipperController` 的 tag 都不会出现，实测三份 logcat 中该 tag 全部无匹配）。

### 2.3 抬腕传感器的提供者（魅族 SensorAux HAL）在本机不存在

- VINTF 声明了 `vendor.meizu.sensor_aux.ISensorAux/default`，但 `vendor/bin/hw` 里没有对应实现（`待查-常驻服务空转.md` 已记录 `Failed to find 'vendor.meizu.sensor_aux.ISensorAux/default'`、200+ 次 5 秒死等）
- 本次在三份日志里再次确认：

```
ServiceManagerCppClient: Service vendor.meizu.sensor_aux.ISensorAux/default didn't start. Returning NULL   (live3.log:18/63，数百次)
DisplayPowerController: mSensorAuxAidl is null                                                            (live3.log:230)
```

即：魅族私有传感器既没有 HAL 提供，也没有任何服务会去创建；**把开关改可见只是让开关"能动"，功能依然不动**。

## 3. 与 MIX4（odin）那次的异同

| | MIX4 / odin（已修） | Xiaomi 15 / dada（本次） |
|---|---|---|
| 双击亮屏断点 | 内核 FTS 驱动**已经会在双击时上报 `KEY_WAKEUP(143)`**；Flyme 的 `fts.kl`/`main_touch.kl` 缺 `key 143 WAKEUP`，事件被丢弃 | 双击位根本没下发到触摸 IC（`/sys/class/meizu/tp/gesture_control` 不存在）→ **IC 不在手势模式，什么都不会上报**；补 keylayout 不够 |
| 修复手段 | keylayout 补 `key 143 WAKEUP`（V1）+ services.jar 注入 `Mix4GestureGate` 做闸门/锁屏判断（V2，未验证） | 需先解决"如何让小米触控进入双击模式"，再处理上报键的映射 |
| 抬手/翻转亮屏 | 同样因魅族私有传感器而隐藏 → RRO 覆写 `config_*SensorType` + 自建监听器 | 完全同构（传感器类型 65538/65539，无覆写） |
| FOD | 用 `ITouchFeature.setTouchMode(0,14,val)` | porter 已用 `mifod/fod-bridge.jar` 桥接（binder 直连 `vendor.xiaomi.hw.touchfeature.ITouchFeature/default`，`setModeValue(touchId=0, mode=10, value)` = MODE_TOUCH_MONITOR） |

**关键洞察**：`ITouchFeature` 就是这块触摸 IC 的"模式控制"入口，FOD 这条已经通了；双击/手势模式同样应该走这里（小米原生实现见底包 `Xiaomi15\system_ext\framework\miui-services.jar`，其中 `ITouchFeature` 出现 5 次、`DoubleTap` 49 次；`system\system\framework\services.jar` 也有 `setModeValue`。而 Flyme 的 system_server 里**没有任何人调用它**——魅族只会写 `/sys/class/meizu/*`）。

## 4. 还需真机确认的 4 项（设备当前离线，均为一分钟命令）

1. `dumpsys sensorservice | grep -iE "pickup|dbtap|wake_gesture|6553"` — 确认确无 65538/65539；确认是否有小米的 `xiaomi.sensor.pickup`(33171036) / `dbtap`(33171045)，它们是抬手亮屏的**替代信号源**

4. `settings get system mz_quick_wakeup_switch; settings get system mz_quick_wakeup_double_click; settings get system raisewakeup_switch`

## 5. 修复方向（按代价从低到高）

1. **RRO 改可见性（先让开关回来）**
   - 覆写 `integer/config_raiseSensorType`、`integer/config_flipSensorType` 为一个"本机存在且能用的"传感器类型；
   - 若要顺带修最省事的那半边，也可覆写 `string/gesture_control_path_string`、`string/touch_panel_sleep_path` 指向小米真实节点（framework 是 `getString` 读取，RRO 可覆盖）。
   - 注意：① 只改 RRO 对抬手亮屏**不够**，`RaiseFlipperController` 注册的监听器语义（值 2/4/5/6/7）是为魅族驱动写死的；② MIX4 V1 已经踩过"用 `requestTriggerSensor`（LIFT）必失败、必须用普通 `registerListener` + `mWakeUp`"的坑。
2. **抬腕/翻转：桥接 SensorAux（真正让它动）**
   - 方案 A（framework hook，成本低）：挂 `RaiseFlipperController` 的构造与 `updateRaiseAndFlipSensor()`，把 65538/65539 换成小米 `pickup`/`dbtap` 传感器，并做值映射（唤醒/息屏），闸门读 `raisewakeup_switch`/`flipwakeup_switch`。
   - 方案 B（services.jar 补丁，可控性高）：仿 MIX4 V2 的 `Mix4GestureGate`，注册小米传感器 → `PowerManager.wakeUp()`，并保留"仅锁屏、仅抬手后短窗口、接近光为负、放下即息屏"的闸门（V2 的教训：闸门与锁屏判断缺一不可，否则亮屏又自动灭或口袋里乱亮）。
3. **双击亮屏（两步）**
   - 第一步：让触摸 IC 进入双击/手势模式 —— 通过 `ITouchFeature.setModeValue(0, <双击模式号>, 1)`（可直接扩展 `MiFodBridge` 的 binder 骨架；具体 mode 号从底包 `miui-services.jar` 里 MIUI 的 `DoubleTap` 实现反查，或在真机上用 TouchFeature 逐个 mode 试）。**注意**：Flyme 的 `mMainGestureControl` 走的是魅族节点，这条路径永远写不进去，所以"启用"必须由桥接层完成，不能指望 `mz_quick_wakeup_switch`。
   - 第二步：确认上报键后补 keylayout —— 若报 143，`Generic.kl` 已有 `key 143 WAKEUP`，无需改动；若报 624+，需新建 `Xiaomi_Touch_Input_0.kl`（或让该设备名的 .kl 把 624 映射成 WAKEUP）。
   - 顺手修 1.2 的默认值不一致：让 `mz_quick_wakeup_switch` 与 UI 保持一致（否则用户看到"开"却什么都没有）。
4. **不要动的地方**：`/system_ext/apex/com.flyme.runtime.apex` 里的 `GestureManagerService` 是 FOD 与手势共用的控制通道，当前 FOD 已由 `MiFodBridge` 独立走 TouchFeature；改它风险大、收益低。

## 7. 补充：能不能直接桥接到小米 HAL？

**结论：可以，而且比 RRO / hook 更干净。** 这台机器上小米侧的两条 HAL 通道都是"活着"的（不是死的），只要把小米的信号翻译成 Flyme 期望的语义（或反过来把 Flyme 的期望喂给小米通道）即可。

### 7.1 小米侧现成的通道（均已在移植包 / 日志中验证）

| 通道 | 证据 | 可解决 |

### 7.2 三条桥接路线（按成本排序）

**路线 A —— daemon 桥（最省事，建议先做）**

完全复刻 `mifod/fod-bridge.jar` 的形态（一个常驻小进程，或用 Nyako 宿主）：

- 抬手：`SensorManager.getDefaultSensor(<pickup/flip_status 类型号>, true)` → 注册监听 → 事件到 → `PowerManager.wakeUp()`；闸门读 `raisewakeup_switch`；放下（对应值）→ `goToSleep()`
- 双击：先用 `ITouchFeature` 打开 IC 的双击模式（或直接订阅 `dbtap` 传感器）→ 事件到 → `wakeUp()`

成本 ~100–200 行；不动 framework / HAL / RRO。缺点：需要常驻；抬手开关仍要靠 RRO 才能显示（Flyme 判可见性只看 65538/65539 是否存在）。

**路线 B —— 自建 sub-HAL（最干净，真正"桥到小米 HAL"）**

写 `sensors.meizu.shim.so`（HIDL `android.hardware.sensors@2.0::ISensors` subhal），`hals.conf` 加一行；它向 framework 注册 **65538（flip）/ 65539（raise）两个 wake-up 传感器**，数据源取小米 `pickup` / `flip_status`（或 `dbtap`），并翻译成魅族语义（抬起 = 2、放下 = 4/5/7；翻转亮 = 1、合上 = 2）。

- 收益：`MzUtils.supportRaiseFlipFeature()` 自动为 true → **设置开关自己出现（连 RRO 都不需要）**；`RaiseFlipperController` 自己注册、自己 `wakeUp()`；Flyme 侧**零改动、零 hook**。
- 成本：C++ subhal 约 300–500 行 + 编译环境（对齐 `android.hardware.sensors@2.0` subhal 头文件、wake-up 标志、batch/FIFO 语义）。

**路线 C —— 双击专用（输入层，可能零代码）**

用 `ITouchFeature` 打开 IC 双击模式后，看驱动是否仍按老路上报按键：MIX4 那台报的是 `KEY_WAKEUP`(143)，而本机 `Generic.kl` 已映射 `key 143 WAKEUP` → 若 dada 也报 143，则**只需把模式打开，一行代码都不用加**；若它只走 sensor（`dbtap`），回到路线 A。

### 7.3 桥不了的地方（必须说清）

- `GestureManagerService` 写 `/sys/class/meizu/tp/gesture_control`、`SystemGesture` 写 `screen_mode_node`：**userspace 无法伪造 /sys 节点**。所以"让魅族这条代码原样工作"只有两条路：改 apex 里的 dex，或 RRO 改路径字符串——而后者字节格式不匹配（魅族写 4 字节小端位图，小米节点是 `1`/`0` ASCII），实际不可行。**双击亮屏靠 Flyme 原路径是不可能的**，必须换到小米通道（路线 A/C）。
- `vendor.meizu.sensor_aux.ISensorAux`：VINTF 声明了但无人实现；若要消除空转、让 `DisplayPowerController` 正常，得自己写一个 shim 服务（与路线 B 是两件独立的事）。
- `vendor/etc/permissions/com.xiaomi.sensor.xml` 声明的 `com.xiaomi.sensor.aidl.jar` 在移植包与小米底包里都不存在（`ui.txt:3049` `Ignore shared library ... does not exist`）→ **没有现成的小米传感器 AIDL Java 客户端库**，桥接要么用标准 `SensorManager` + 私有 type 号，要么直接 binder。

### 7.4 真机确认清单（3 条）

1. `dumpsys sensorservice | grep -iE "dbtap|pickup|flip_status|xiaomi.sensor"` → 拿确切 type 号（MIX4 同族预期：pickup 33171036、dbtap 33171045；本机已见 screen_down 33171037 / knuckle 33171038 / gpd 33171120）

`65538/65539` 是**魅族私有传感器**，本机（小米硬件）不存在 → `supportRaiseFlipFeature()` 返回 false → 开关被 `removePreference` 掉。**这就是设置里没有选项的原因**：不是设置项缺失，而是"能力探测"失败后主动隐藏。

SystemUI 侧读的是同一份资源（`com.flyme.keyguard.RaiseFlipperController:206-210`），所以这两个资源是**唯一的开关**：

```java
int flipType  = resources.getInteger(getIdentifier("config_flipSensorType",  "integer", "android"));
int raiseType = resources.getInteger(getIdentifier("config_raiseSensorType", "integer", "android"));
this.mFlipSensor  = mSensorManager.getDefaultSensor(flipType, true);
this.mRaiseSensor = mSensorManager.getDefaultSensor(raiseType, true);
// 218-219：监听设置项，开关一变就注册/注销
mRaiseWakeupOn = Settings.System.getIntForUser(cr, "raisewakeup_switch", 0, -2) == 1;
mResolver.registerContentObserver(Settings.System.getUriFor("raisewakeup_switch"), false, mObserver);
```

**修复：用静态 RRO 覆盖这两个 `android` 资源**，指向本机真实存在、且对 Flyme 判断"惰性"的传感器：

| 资源 | 原值 | 覆盖为 | 理由 |
|---|---|---|---|
| `config_flipSensorType` | 65538 | **8（proximity）** | 存在且是 wakeup 传感器；取值只有 `0.0/5.0` |
| `config_raiseSensorType` | 65539 | **8（proximity）** | 同上 |

惰性论证（对照 `RaiseFlipperController` 的判断）：flip 监听器只在 `i==1 && !isInteractive` 时唤醒、`i==2 && isInteractive` 时灭屏；raise 监听器在 `i==2` 时才会去注册接近传感器、在 `i==4||5` 且 `mWakeupByRaise/mWakeupByFlip` 为真时才灭屏。proximity 只会给出 `0`/`5`，而这两个标志位只有 Flyme 自己的监听器唤醒时才会置位 → **SystemUI 侧全程惰性**，真正的抬手唤醒仍由 `MiGestureBridge` 负责。开关一旦可见并打开，`raisewakeup_switch` 同时驱动桥与 Flyme 两侧。

#### (2) 开关的三个入口，以及"为什么有的页面看不到"

| 入口 | 实现 | 有没有能力检测 |
|---|---|---|
| **独立页「抬腕亮屏」** | `MzSettingsActivity$FlymeRaiseFlipSettingsActivity` + `FlymeRaiseAndFlipFragment`（`res/xml/flyme_raise_flip.xml`，label = `raise_flip_config_title`） | **没有**，无条件 `addPreferencesFromResource` + 读 `flipwakeup_switch/raisewakeup_switch` |
| 显示与亮度 → 抬腕亮屏 | `FlymeRaiseFlipController.getAvailabilityStatus()` | **有**：`supportRaiseFlipFeature(ctx) ? 0 : 3` |
| 息屏显示/锁屏 → 抬腕亮屏 | `AODAndLockScreenSettings:158-165` | **有**：不满足就 `removePreference` |

所以"设置里没有"的准确表述是：**独立页一直有，但常规两个入口被能力检测隐藏了**。而检测里还有一个 OR 条件来自实验室：

```java
// FlymeLabHelper.isFlymeLabHasFeature("com.android.settings.raiseflip")
//   → 查 content://com.meizu.flymelab.features/packageNameList
```

本机没装 FlymeLab，provider 不存在 → `query()` 返回 null → 该条件为 false（不影响显示）。也就是说**唯一挡住开关的就是那两个传感器资源**。

#### (3) 运行时动态 RRO：可用，但**不跨重启**（早先的失败是偶发）

早先在这台机器上 `cmd overlay fabricate` + `enable` 失败过（`SecurityException: commit failed` + `logcat: service 'idmap' died`，用确定可覆盖的资源做对照实验也一样）。**但本次实测完全可用**：

```sh
cmd overlay fabricate --target android --name mzflip_test  android:integer/config_flipSensorType  0x10 8   # exit=0
cmd overlay fabricate --target android --name mzraise_test android:integer/config_raiseSensorType 0x10 8   # exit=0
cmd overlay enable --user 0 com.android.shell:mzflip_test
cmd overlay enable --user 0 com.android.shell:mzraise_test
cmd overlay lookup android android:integer/config_flipSensorType   # → 8
cmd overlay lookup android android:integer/config_raiseSensorType  # → 8
```

`cmd overlay dump` 显示它们是真·fabricated overlay（注意 `.frro` 与 `overlays.xml` 里的记录都在）：

```
com.android.shell:mzflip_test:0
  mTargetPackageName: android   mState: STATE_ENABLED   mIsFabricated: true
  mBaseCodePath: /data/resource-cache/com.android.shell-mzflip_test-z9rp.frro
IDMAP OF com.android.shell:mzflip_test
  target path : /system/framework/framework-res.apk
  Mapping: 0x010e01db -> integer 0x00000008 (integer/config_flipSensorType)
```

（撤销：`cmd overlay disable com.android.shell:mzflip_test` 与 `...mzraise_test`。）

> ⚠️ **更正（同日晚间实测）**：本文前面写的"状态写进 `/data/system/overlays.xml` → 重启不丢"是**错的**。
> DSU 重启一次后实测：`cmd overlay list android` 里 `mzflip_test/mzraise_test` **消失**，
> `cmd overlay lookup` 又变回 **65538 / 65539** —— AOSP 的 fabricated overlay **不跨重启**
> （`.frro` 与 `overlays.xml` 里的记录还在，但开机不再注册它们）。
> 用户侧的表现就是：**重启后设置里的开关又不见了**。详见 8.8。

**注意 overlay 对"哪些 Resources 可见"有区别**（实测，同一进程内三种取法）：

```
ActivityThread.systemMain().getSystemContext().getResources()    → flip=65538 raise=65539   （不吃 overlay）
Resources.getSystem()                                            → flip=65538 raise=65539   （不吃 overlay）
PackageManager.getResourcesForApplication("android")             → flip=8     raise=8       （吃 overlay ✓）
```

即 `Resources.getSystem()` 这个全局单例是按"无覆盖"构建的（app_process 写的探针用它读会误判）。
设置里的 `MzUtils.supportRaiseFlipFeature()` 用的是 `ctx.getResources()`（应用自己的 Resources），走的是能吃覆盖的那条路。

#### (4) KernelSU 模块为什么塞不进 `/product/overlay`（给移植方的坑）

`/product/overlay` 在这台机器上**本身就是一个 overlayfs 挂载点**：

```
overlay /product/overlay overlay ro,lowerdir=/mnt/vendor/mi_ext/product/overlay/:/product/overlay,redirect_dir=on
/dev/block/dm-7 /mnt/vendor/mi_ext erofs ro        ← 只读，写不进去
```

KSU 的模块文件挂载会被这层挂载**遮住**（实测：模块文件确实在 `/data/adb/modules/sensortypeoverlay/product/overlay/`，但 `/product/overlay/SensorTypesOverlay.apk` 不存在、`cmd overlay list` 里也没有它）。
→ 覆盖包必须**进 ROM**（`product/overlay/` 或 `vendor/overlay/`，后者是 erofs 上的普通目录），或者用上面那条 `cmd overlay fabricate` 的运行时做法。

ROM 内静态覆盖本身是有效的，证据是同目录下魅族自己的 RRO：

```
cmd overlay list android  → [x] android.overlay.mz   （targetPackage=android, isStatic=true, 无 overlayable 声明）
cmd overlay lookup android android:array/config_ntpServers
  → ntp://time-a.nist.gov, ntp://time.apple.com, ... ntp://hshh.org   ← 正是该 RRO 里的值
```

也就是说**与本项目覆盖包形状相同的静态 APK 能覆盖 framework-res 的私有非 overlayable 资源**，放进 `product/overlay/` 即可（本仓库 `sensortype-overlay/build/SensorTypesOverlay-signed.apk` 就是它）。

#### (5) 开关不起作用：桥没有读设置（已修复并实测）

原实现无条件下发 `setModeValue(0,14,1)`，所以「双击亮屏」开关关掉后依然生效。改为**跟随 Flyme 设置项**（同一套 key，与 Settings/SystemUI 完全一致）：

| `mz_quick_wakeup_double_click` | `!= 0` → `setModeValue(0,14,1)`；`== 0` → `setModeValue(0,14,0)` |

### 8.7 抬手亮屏"开机后失效"：KSU 自启太早导致的 power 服务竞态

把桥做成开机自启后，出现了一个很隐蔽的现象：**pickup 事件收得到，但永远不唤醒**。日志是这样的：

```
MiGestureBridge: pickup event value=1.0 screenOn=false      ← 拿起事件到了、熄屏也对
（之后什么都没有：既没有 wakeUp 成功的日志，也没有任何失败告警）
```

`wakeUp()` 的三个出口**每个都会打日志**（`wakeUp(time,reason) ok` / `wakeUp(time) ok` / `fallback input keyevent 224 issued`，
失败时 `call()` 还会打 `Log.w`），一条都没有 → **它压根没被调用**。而 `screenOn` 是

```java
boolean screenOn = powerManager != null && powerManager.isInteractive();   // ← null 时永远打印 false
```

算出来的，所以 `screenOn=false` 有两种可能。日志没打印 `powerManager`，但结合"三出口都没日志"可以反推：
**进去时 `powerManager == null`**，条件 `v == 1.0f && powerManager != null && !screenOn` 直接被短路。

为什么 null：看模块脚本落地的时间 ——

```
=== supervisor start Sun Oct 11 11:41:10 CST 2026 (uptime 5.60s) ===
```

**开机 5.6 秒就被 KSU 的 `service.sh` 拉起来了**。此时 `system_server` 的 Java 服务还没注册完，
`ContextImpl.getSystemService(POWER_SERVICE)` 内部把 `ServiceNotFoundException` 吞掉、返回 **null**，
而且**不会自己恢复**；而 `sensorservice` / `vendor.xiaomi.hw.touchfeature` 是 init 起的 native 服务，早就可用 ——
于是"能收到 pickup 事件、却永远唤不醒"。手动在开机后启动的实例一切正常，正是这个原因
（早期那次"手动启动已验证"的测试恰好绕过了这个竞态）。

**修复（两道保险）**：

1. 桥内部：启动时**最多等 60 秒**等 power 服务就绪；之后每次传感器事件、以及每 10 分钟的重申任务里
   再调 `ensurePower()` 兜底补取，补到时顺便**重读一次设置**（开机早期那次读设置也可能只拿到默认值）。
2. 模块脚本：`service.sh` 先等 `sys.boot_completed=1`（最多 180 秒）再起桥。

实测（重启桥后）：

```
MiGestureBridge: powerManager acquired (late)
MiGestureBridge: [late-power] mz_quick_wakeup_double_click=1 raisewakeup_switch=1 flipwakeup_switch=1 -> doubleTap=true raise=true
MiGestureBridge: register pickup -> true
MiGestureBridge: ready (doubleTap=true raise=true)
MiGestureBridge: pickup event value=1.0 screenOn=false power=true
MiGestureBridge: wakeUp(time,reason) ok                      ← ✅ 抬手亮屏
MiGestureBridge: pickup event value=2.0 screenOn=true  power=true   ← 放下时屏已亮，不重复唤醒
```

### 8.8 「设置里的开关又不见了」：fabricated overlay 不跨重启

同日晚间（DSU 重启一次之后）复测，`uptime 37 min` 的新会话里：

```
cmd overlay list android | grep mzflip                              →  （无输出：覆盖没了）
cmd overlay lookup android android:integer/config_flipSensorType    → 65538
cmd overlay lookup android android:integer/config_raiseSensorType   → 65539
settings get system mz_quick_wakeup_double_click                    → 0
```

即：**`cmd overlay fabricate` 造出来的覆盖重启后不会被重新注册**（AOSP 行为；`.frro` 与
`/data/system/overlays.xml` 里的记录都还在，但开机不再加载它）。两个资源回到魅族私有值 →
`MzUtils.supportRaiseFlipFeature()` 又变 false → 常规入口里的「抬腕/翻转亮屏」开关再次被
`removePreference` 移除。

**修法（两道，本项目都做了）**：

1. **开机自动重建**（本次新增）：`migesture` 与 `sensortypeoverlay` 两个 KernelSU 模块的
   `service.sh` 都在 `sys.boot_completed=1` 之后执行一遍 `fabricate + enable`
   （按名字发现覆盖包名，幂等，最多 30 次 × 2s 重试），最后 `am force-stop com.android.settings`
   让设置重读资源。**装任一模块即可自愈**。
2. **ROM 内静态 RRO**（永久、不依赖 root）：把 `sensortype-overlay/build/SensorTypesOverlay-signed.apk`
   放进 `product/overlay/`（或 `vendor/overlay/`）。

重新应用后真机 UI dump（设置 → 显示与亮度，滚到底）：

```
自动锁屏 10 分钟后
注视时不锁屏 关闭
双击亮屏 关闭          ← 一直在，见 8.9
抬腕亮屏 开启          ← 恢复
屏幕旋转 开启
```

### 8.9 顺带查清：「双击亮屏」开关的可见性跟这两个资源**无关**

- **显示与亮度**页（`mz_display_settings.xml`）里「双击亮屏」的 preference key 是
  `quick_wakeup_double_click`，由 `FlymeDoubleClickWakeUpController` 控制，可见性判断是：

  ```java
  public int getAvailabilityStatus() {
      return mContext.getResources().getBoolean(android.R.bool.config_automatic_brightness_available) ? 0 : 3;
  }
  ```

  本机该布尔资源解析值是 **true**（framework-res 里的默认值是 false，被静态覆盖顶成了 true）→ 恒可见；
  真机 UI dump 也证实它在，勾选状态跟随 `mz_quick_wakeup_double_click`。**它不会因为覆盖丢失而消失。**
- 「息屏显示和锁屏」页（`aod_and_lockscreen_settings.xml`，Activity
  `MzSettingsActivity$AODAndLockScreenSettingsActivity`）在本移植上**打不开**：`dumpsys package`
  里能看到这个组件，但 `am start` 直接报 `Activity class ... does not exist`
  （`pm enable` 之后再试仍然如此）→ 这页上的开关实际不可达。该页 Java 逻辑里
  `quick_wakeup_double_click` 只在 `MzUtils.isEasyModeOpened()`（`mz_easy_mode == 1`）时才被移除，
  设备上 `mz_easy_mode` 未设置（=0），所以不是这个原因；同页的 `raise_flip` 则同样受
  `supportRaiseFlipFeature()` 约束。
- 「副屏」页（`subscreen_settings.xml`）另有一个独立的「双击亮屏」（key
  `subscreen_double_click_wakeup`），属于魅族副屏硬件功能，本机没有该硬件。
- 结论：**要看/改「双击亮屏」请走 设置 → 显示与亮度**；重启后会消失的是「抬腕/翻转亮屏」，不是它。

## 9. 结论与修复清单

| 功能 | 根因 | 修复 | 状态 |
|---|---|---|---|
| **双击亮屏** | 触摸 IC 从未进入双击模式：Flyme 只写不存在的 `/sys/class/meizu/tp/gesture_control`，而小米侧真正的开关是 `ITouchFeature.setModeValue(0,14,1)`（`Touch_Doubletap_Mode`） | `MiGestureBridge` 下发 `setModeValue(0,14,1)` | **真机已验证**（`getevent` 抓到 `KEY_WAKEUP` + 屏幕点亮） |
| **抬手亮屏** | Flyme 依赖魅族私有传感器 65538/65539（`MzUtils.supportRaiseFlipFeature()` 要求两者非 null），本机不存在 → 开关隐藏、`RaiseFlipperController` 注册 null | `MiGestureBridge` 监听 `xiaomi.sensor.pickup(33171036)` → `PowerManager.wakeUp()` | **真机已验证**（熄屏拿起亮屏 / 放下不误唤醒 / 屏已亮不重复唤醒） |
| **设置里没有「抬手/翻转亮屏」开关** | 常规两个入口（`AODAndLockScreenSettings`、`FlymeRaiseFlipController`）用 `supportRaiseFlipFeature()` 判定能力，而该判断读 `android:integer/config_flipSensorType(65538)`/`config_raiseSensorType(65539)` —— 本机没有这两种魅族私有传感器 → 判定不支持 → 隐藏（独立页 `FlymeRaiseAndFlipFragment` 没有检测，一直存在） | 用覆盖把这两个资源指向 `proximity(8)`：运行时 `cmd overlay fabricate`+`enable`（免重启；**不跨重启**，已由两个模块的 `service.sh` 开机自动重建，见 8.8）或 ROM 内静态 RRO（永久） | **运行时覆盖已实测生效**（`lookup` = 8，`cmd overlay dump` 显示 idmap 映射到 `0x010e01db -> 8`）；独立页已成功拉起 |
| **双击开关关掉仍生效** | 桥原来无条件打开 IC 双击模式，没有读设置 | 桥跟随 `mz_quick_wakeup_double_click` / `raisewakeup_switch` / `flipwakeup_switch` | **真机已验证**（开关 → 驱动 `Touch_Doubletap_Mode` 0/1 逐条对应） |
| **抬手亮屏"开机后失效"** | KSU 的 `service.sh` 在 **uptime 5.6s** 就起了桥，那时 `system_server` 的 power 服务还没注册，`getSystemService(POWER_SERVICE)` 返回 **null 且不会自恢复** → pickup 事件收得到、`wakeUp()` 永不执行（三出口都无日志，`screenOn=false` 是 null 造成的假象） | 桥内 `ensurePower()`（启动等 60s + 每次事件/每 10 分钟兜底补取，补到后重读设置）+ `service.sh` 等 `sys.boot_completed=1` | **真机已验证**（`power=true` → `wakeUp(time,reason) ok`） |
| 翻转亮屏（附） | 本机没有 `flip_status` 传感器，只有 `screen_down(33171037)`（注册即上报 `1.0`，映射它会被 Flyme 当成"翻到正面"而立即亮屏，危险） | 未做；如需可仿照抬手写桥 | 可选 |

所有修复都不需要动 framework / HAL / RRO 之外的东西：双击与抬手是「一个 jar + init 服务（或 KernelSU 模块）」，开关可见性是「一个静态 RRO」。三个交付物都在 `migesture/` 与 `sensortype-overlay/` 下，`dist/` 里是可直接安装的模块包。

**A. ROM 内置（正式）**：把 `migesture.jar` 放到 `/system/etc/migesture/`、`migesture.rc` 放到 `/system/etc/init/`（照抄 `/system/etc/init/mifod.rc` 的写法：`app_process64`、`class late_start`、`user root`、`seclabel u:r:su:s0`、`setenv CLASSPATH`）；把 `SensorTypesOverlay-signed.apk` 放进 `product/overlay/`（与 `FrameworksResCommon_Mz.apk` 同目录）或 `vendor/overlay/`。

**B. KernelSU 模块（桥可用；覆盖包在 DSU 下进不去）**：`su -c 'ksud module install /data/local/tmp/migesture-ksu.zip'` 装桥 → 重启 Flyme 生效。
覆盖包的模块（`sensortypeoverlay-ksu.zip`）在本机**不生效**，原因见 8.6(4)：`/product/overlay` 是 `mi_ext` 的 overlayfs 挂载点，KSU 挂上去的文件被遮住。

**C. 运行时覆盖（免重启，DSU 测试首选）**：

```sh
su -c 'cmd overlay fabricate --target android --name mzflip_test  android:integer/config_flipSensorType  0x10 8'
su -c 'cmd overlay fabricate --target android --name mzraise_test android:integer/config_raiseSensorType 0x10 8'
su -c 'cmd overlay enable --user 0 com.android.shell:mzflip_test'
su -c 'cmd overlay enable --user 0 com.android.shell:mzraise_test'
su -c 'am force-stop com.android.settings'      # 让设置重新读资源
```
**注意：fabricated overlay 不跨重启**（见 8.8），所以本方式只在当次开机内有效；长期用请走方式 A（ROM 静态 RRO，永久），
或者装 `migesture` / `sensortypeoverlay` 模块 —— 它们的 `service.sh` 会在每次开机自动重建这份覆盖。
撤销：`cmd overlay disable --user 0 com.android.shell:mzflip_test`（另一个同理；覆盖包名可能随调用者身份变化，
先 `cmd overlay list android | grep mzflip` 确认实际包名）。

> ⚠️ 本项目是在 **DSU 里测 Flyme**：`adb reboot` 会直接退出 DSU 回到主系统，
> 所以脚本/命令**不要自己发 reboot**，重启交给使用者自己的 DSU 流程。
> KernelSU 模块装完后在 `modules_update/` 暂存，**下一次进 DSU 时才生效**；静态 RRO 同理只在开机扫描时注册。

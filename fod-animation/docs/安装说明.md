# FOD 指纹解锁动画 —— 注入魅族 FOD 手势（v4）

**当前状态**：注入通道已验证可用（有日志实证）。v4 换成了**最可靠的触发源** —— 指纹 HAL 自己打印的
FOD 触摸日志，不再依赖触摸屏是否上报 FOD 区域。

---

## 1. 已经证实的事实

### 1.1 动画只有一个入口

全 ROM 搜 `showFingerprintDownAnim()` 的调用点，只有两处，都在 `MzGestureController`：

```
com\flyme\keyguard\MzGestureController.java:438  ...showFingerprintDownAnim();   (宽指纹 左/右/中)
com\flyme\keyguard\MzGestureController.java:441  ...showFingerprintDownAnim();   (普通)
```

其余全是链路上的转发（`KeyguardUpdateMonitor:3701 → AuthController:1182 → UdfpsController:1102
→ UdfpsControllerOverlay:751 → UdfpsAnimationViewController:231 → UdfpsKeyguardViewLegacy:484
→ FlymeFpAuthAnimView.startDownAnimation()`）。**没有任何"真实触摸自动触发动画"的旁路。**

### 1.2 注入通道已经打通（2026-10-09 21:19:03）

```
21:19:03.648 14345 14712 I MzGestureHelper: onGestureTrigger data:161 MotionEvent:null
```

pid 14345 = SystemUI。`gesture_manager` 服务在、能调、uid=0 无权限拦截，413 被正确翻译成 161 并送达 SystemUI。

### 1.3 v3 修掉的两个问题

| 问题 | 说明 | 修法 |
|---|---|---|
| NPE | 服务广播给所有注册者，`com.flyme.systemuitools.windowmode.WindowMode$GestureCallback` 是 Kotlin、`motionEvent` 非空，传 null 抛 NPE 并**可能中断后续回调派发** | 传真实动作的 MotionEvent（FOD 中心 600,2036） |
| 抬起漏发 | NPE 让 `pulse` 中途退出，162 没送，系统停在 finger-down | 按下/抬起各自兜底，保证 162 一定发出 |

### 1.4 v4 修掉的根本问题：触发源找错了

21:44 的 watch 实测输出：

```
[fod] input 设备: [..., event7=Xiaomi_Touch_Input_0, ...]
[fod] /dev/input/event7 上报多点触控坐标
（然后按压 FOD 区域，没有任何输出）
```

两个原因：

1. **小米把 FOD 触摸交给指纹 HAL，触摸屏设备（event7）不上报 FOD 区域的按下** —— 所以按坐标判断收不到。
2. 我的"手指按下"判定只认 `ABS_MT_TRACKING_ID`，且坐标日志被限流到 10 秒一次，所以按了也看不到。

**正确的触发源在指纹 HAL 的日志里**（10-08 的日志中按下/抬起成对出现，6 次触摸 6 对）：

```
I QFP: onPointerDown: entry pointerId=0 x=565 y=2027 minor=0.000000 major=0.000000
I QFP: onPointerUp: entry pointerId=0
```

坐标 x∈[555..639] y∈[1996..2086]，正好落在 ROM 的 `sensorBounds (518,1954)-(682,2118)` 里 ——
确认这就是 FOD 区域的真实触摸事件，而且**只有真手指按上才会出现**。

## 2. 现在怎么用

### 2.1 推荐：logwatch（真手指按 FOD 就出动画）

```sh
su -c "sh /data/local/tmp/fod_paste.sh logwatch"
# 然后正常把手指按在指纹上
```

它会监听 `QFP onPointerDown/onPointerUp`，按下注入 161、抬起注入 162。

**成功的样子**：
```
[fod] logwatch: 监听 logcat QFP onPointerDown/onPointerUp -> 注入 161/162
[fod] HAL onPointerDown -> 161
[fod] FOD 按下 -> 161 (startDownAnimation)
I MzGestureHelper: onGestureTrigger data:161
D FlymeFpAuthAnimView: startDownAnimation mAnimationType=3
```
+ 屏幕出动画。

### 2.2 手动验证（不按指纹，直接注入）

```sh
su -c "sh /data/local/tmp/fod_paste.sh pulse 3000"
```

### 2.3 诊断

```sh
su -c "sh /data/local/tmp/fod_paste.sh raw 15"    # 各 input 设备上报的 ABS/KEY 取值范围
su -c "sh /data/local/tmp/fod_paste.sh dump 15"   # 实时打印触摸坐标（按 FOD 和按别处对比）
```

`watch`（按触摸坐标判断）也保留，但在这台机器上 FOD 不上报给触摸屏，所以优先用 `logwatch`。

### 2.4 常驻 / 开机自启

验证通过后：KernelSU 管理器里安装 `fodgesture-module.zip`（模块的 `service.sh` 开机直接拉起 `logwatch`），
日志在 `/data/local/tmp/fodgesture/watch.log`。

**开机时序（v4-r2 已修）**：旧版 `service.sh` 是"等 `sys.boot_completed` 再 `sleep 20`"，所以**开机后
前 20~30 秒按指纹不会有动画** —— 那段时间根本没有进程在监听。现在改成：

1. `service.sh` 在 `late_start` 一执行就启动（早于 `boot_completed`），**不再等待**；
2. 用 `while true` 看门狗保活（logcat 未就绪时退出，2 秒后重试，直到起来）；
3. jar 侧把 `gesture_manager` 的 binder 解析**推迟到第一次触摸时**（带 10 秒重试），
   所以在极早期启动也不会失败。

日志里能看到时间线：

```
=== supervisor start Sat Oct 10 19:47:0x GMT+08:00 2026 (uptime 42s) ===   ← 开机即起
=== boot_completed at ... ===
```

剩下的启动延迟只有第二道门：ROM 自己要等锁屏开始监听指纹
（`MzGestureController:428` 的 `isFingerprintDetectionRunning()`，即 `mFingerprintRunningState == 1`），
这段由生物识别 HAL + keyguard 初始化决定，注入器无法加速。所以正确的预期是：
**开机后锁屏一可解锁（FOD 首次能响应指纹）时，动画就已经在了**。

## 3. 剩下的静默守卫（万一 logwatch 还没动画）

从 `onGestureTrigger` 到动画之间**没有任何日志**，失败都是静默 `return`：

| 步 | 位置 | 静默失败条件 |
|---|---|---|
| 1 | `MzGestureController:405` | `fingerprintUsedAsUnlock()` false |
| 2 | `MzGestureController:428` | `isFingerprintDetectionRunning()` false |
| 3 | `UdfpsControllerOverlay:748` | `!isShowing()` / `getAnimationViewController() == null` |
| 4 | `UdfpsAnimationViewController:230` | view 不是 `UdfpsKeyguardViewLegacy` |
| 5 | `UdfpsKeyguardViewLegacy:485` | `mFlymeFpAuthAnimView == null` |

只有最后 `FlymeFpAuthAnimView.startDownAnimation` 会打日志。用 `logwatch` 时，注入时刻与真手指按下同刻，
2、3 两道门天然是开的，所以如果仍无动画，问题就在 3–5 步（浮层/view 侧），届时按日志继续查。

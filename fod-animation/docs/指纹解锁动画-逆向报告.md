# Flyme 锁屏指纹「解锁动画」：为什么不动，怎么修

- 设备：Xiaomi 15（`dada` / `24129PN74C`）+ Flyme 12 移植，Android 16
- 样本：`_sysui/SystemUI.apk`（设备直拉，73,678,743 B）、`_settings_apk/Settings.apk`（12.1.0 样本）
- 日志：`ui.txt`(D 级 16:20–16:23)、`live_unlock.log`(19:44)、`live2.log`/`live3.log`(20:03)、`_vib/nyako_check.log`(23:01)
- 方法：jadx 反编译 + 设备 dex `dexdump` 核对签名 + 全量字符串 grep + 5 份 logcat 交叉对比

---

## 一句话结论

**动画资源、SVGA 播放器、开关设置全是好的，坏的是「触发信号」。**

Flyme 只在收到 **Meizu 手势服务的 161（按下）/162（抬起）** 时才启动这个动画，而这台小米 15 的移植 ROM **从来不产生该手势事件**——
移植只把小米触控 IC 切到 FOD 模式（`MiFodBridge`），从没把触摸喂给 Meizu 的 `gesture_manager`。

修复 = 在 `UdfpsController.onFingerDown/onFingerUp` 上**重放 161/162**，走 Flyme 原有动画链路。已做成 NyakoHook 插件 `fpanim`（见 `fpanim-out/`）。

## 3. 为什么在你的机器上断了（硬证据）

### 3.1 服务拿到了、回调注册了，但事件永远不来

`ui.txt`（同一次 SystemUI 生命周期，pid **4588**）：

```
16:21:03.205  4588 W MzGestureHelper: gestureManager = android.view.IGestureManager$Stub$Proxy@46e42dd
16:21:03.206  4588 W MzGestureHelper: gestureManager.registeCallback(mGestureCallback,MzGestureHelper)
```

**注意时间点**：回调是 16:21:03 注册的，而指纹触摸发生在 16:22:14 / 16:22:26 / 16:22:35 / 16:22:40 / 16:22:43 / 16:23:05 —— **全在注册之后**。

### 3.2 同一批日志里：触摸有，手势没有

| 日志 | 指纹触摸证据 `QFP: onPointerDown` | Meizu 手势 `onGestureTrigger` / `handleGesture` | `MzGestureHelper` 总行数 |
|---|---|---|---|
| `ui.txt` | **11** | **0 / 0** | 2（仅上面两条启动日志） |
| `live2.log` | 1 | **0 / 0** | 0 |
| `live3.log` | 1 | **0 / 0** | 0 |
| `live_unlock.log` | 0 | **0 / 0** | 0 |
| `_vib/nyako_check.log` | 0 | **0 / 0** | 0 |

`onGestureTrigger` 是 **`Log.i`**（`MzGestureHelper` 这个 tag 在每份日志里都抓得到，见 3.1 那两行），所以「0 次」是有效证据，不是日志级别过滤造成的假象。

⇒ **触摸发生 → 手势 161/162 从未送达 → `startDownAnimation()` 从未执行 → 没有解锁动画。**

### 3.3 那 161/162 本来谁产生？为什么移植机没有

- Meizu 原生：触摸 → Meizu 触摸栈（`mfp-daemon` 读 `/dev/input`、Meizu 触摸 HAL / `vendor.meizu.sensor_aux.ISensorAux`）→ 判定 FOD 区域按下 → 注入手势 413 → `gesture_manager` 广播。
- 这台机器的旁证（驱动层**确实**有触摸，缺的是上层转换那一步）：
  ```
  E mfp-daemon: [threadLoop] event.type:1 code:14a event.value:1     ← 原始触摸事件
  E mfp-daemon: [threadLoop] event.type:3 code:35  event.value:...   ← mTouchCenterX
  E mfp-daemon: [threadLoop] mFodTouchPollFd[2] break
  ```
  但 `vendor.meizu.sensor_aux.ISensorAux/default` 在 system_server 里一直 `Waiting for service …`（**服务根本不存在**）。
- 移植方给的东西是 `MiFodBridge`（`/system/etc/mifod/`，root/app_process，tag `MiFodKeyguardGate`），它只做两件事：把**小米**触控 IC 切进 FOD 模式（`vendor.xiaomi.hw.touchfeature.ITouchFeature.setModeValue(0, 10, 1|2|0)`、`vendor.xiaomi.hardware.fingerprintextension.IXiaomiFingerprint.extCmd(4, …)`），并在锁屏时轮询重试。**它从不发出 Meizu 手势。**

> 换句话说：小米的超声波 FOD 靠 HAL/IRQ 自己就能完成认证，所以「指纹解锁能用」；但 Meizu 的动画是**手势驱动**的独立装饰层，移植时这一层没人补上 —— 这就是「能解锁、没动画」的原因。

## 4. 修复思路：找一条「必经」的替代信号

穷举 `UdfpsController` 后确认 `onFingerDown` / `onFingerUp` 是**两条输入路径共同的终点**：

```
屏幕亮（锁屏）  UdfpsController.onTouch(ACTION_DOWN/UP)        → onFingerDown(...)     (UdfpsController.java:542 / 528)
AOD 息屏        DozeSensors 注册的 udfps long-press 传感器
                  → DozeTriggers.onSensor → AuthController.onAodInterrupt
                    → UdfpsController.onAodInterrupt (811) → onFingerDown(...)        (UdfpsController.java:852)
```

而且 `onFingerDown` 正是**把坐标交给 HAL 去启动认证**的那一步：

```java
// UdfpsController.java:925
this.mFingerprintManager.onPointerDown(j, mSensorProps.sensorId, i, f, f2, f3, f4, f5, j2, j3, z);
```

所以「指纹能解锁」⇔「`onFingerDown` 一定被调用」。日志直接给出 HAL 侧的印证：

```
I QFP: onPointerDown: entry pointerId=0 x=532 y=2123 minor=0.000000 major=0.000000
I QFP: onPointerDown: entry pointerId=0 x=640 y=2075 minor=0.000000 major=0.000000
I QFP: onPointerUp:   entry pointerId=0
```

⇒ **在 `onFingerDown` 里补一次 `showFingerprintDownAnim()`、在 `onFingerUp` 里补一次 `hideFingerprintDownAnim()`，就等价于 Meizu 的 161/162**，而且走的是 Flyme 原有链路，所有下游判断原样保留：

- 当前 UDFPS 视图不是 `UdfpsKeyguardViewLegacy`（如应用内指纹弹窗）→ 自动 no-op
- `fingerprint_animation = -1`（"无"）→ `FlymeFpAuthAnimView` 自己 return，不播
- 认证失败/出错 → `UdfpsKeyguardViewControllerLegacy` 原有的 `onBiometricAuthFailed/onBiometricError` 仍会隐藏动画（不动认证逻辑，只是补触发）

## 5. 实现：NyakoHook 插件 `fpanim`

四条规则（签名用**设备自己的 dex** `dexdump` 逐字核对过，不是靠猜；为什么是这四条见 §5.2）：

```
com.android.systemui.biometrics.UdfpsController#onFingerDown   (JIFFFFFJJZ)V                  → slot 0
com.android.systemui.biometrics.UdfpsController#onFingerUp     (JLandroid/view/View;IFFFFFJJZ)V → slot 1
com.android.systemui.biometrics.UdfpsController#onTouch        (JLandroid/view/MotionEvent;)Z  → slot 2   ← 主触发
com.android.systemui.biometrics.UdfpsController#onAodInterrupt (IIFF)V                        → slot 3
```

规则里写法（接收者前置为 `Ljava/lang/Object;`，与框架既有插件一致）：

```c
{ NYAKO_OP_REPLACE_METHOD, "com.android.systemui.biometrics.UdfpsController",
  "com.nyako.hooks.FpAnimHook", "onFingerDown",   "(Ljava/lang/Object;JIFFFFFJJZ)V" },
{ NYAKO_OP_REPLACE_METHOD, "com.android.systemui.biometrics.UdfpsController",
  "com.nyako.hooks.FpAnimHook", "onFingerUp",     "(Ljava/lang/Object;JLandroid/view/View;IFFFFFJJZ)V" },
{ NYAKO_OP_REPLACE_METHOD, "com.android.systemui.biometrics.UdfpsController",
  "com.nyako.hooks.FpAnimHook", "onTouch",        "(Ljava/lang/Object;JLandroid/view/MotionEvent;)Z" },
{ NYAKO_OP_REPLACE_METHOD, "com.android.systemui.biometrics.UdfpsController",
  "com.nyako.hooks.FpAnimHook", "onAodInterrupt", "(Ljava/lang/Object;IIFF)V" },
```

替换体（`dex/com/nyako/hooks/FpAnimHook.java`）逻辑：

1. **先跑原方法** `NyakoBridge.invokeOriginal(slot, thiz, args)` —— 认证流程零改动；
2. 再反射调 `thiz.showFingerprintDownAnim()` / `thiz.hideFingerprintDownAnim()`（这两个方法在 `UdfpsController` 上是 public，见 dex）；
3. **AOD 特例**：AOD 下没有真实抬手，`UdfpsController.tryAodSendFingerUp()` 会在按下 1 秒后**合成**一次 `onFingerUp(requestId, touchOverlay)`（`pointerId = -1`）。hook 里对 `pointerId < 0` **跳过隐藏**，让动画一直播到认证出结果（成功 → overlay 隐藏；失败 → 原有回调隐藏），否则 AOD 动画会在 1 秒后被砍断。
4. 日志 tag `NyakoFpAnim`，每次触摸打印一行，方便验证。

### 5.1 第一次装完没生效的原因：框架的插件清单缓存（实测踩到）

插件装好、SystemUI 也重启了，但按指纹没有任何 `NyakoFpAnim` 日志 —— 原因是**框架的插件缓存没有失效**：

```
/data/local/nyako/state/manifest.json   之后所有进程直接信任的插件清单
/data/local/nyako/state/scopes          作用域门禁（决定哪些进程被注入）
```

`nyako_core.cpp` 的 `nyako_framework_init()`（1935-1951 行）：

```cpp
bool scopes_present = (access(NYAKO_STATE_DIR "/scopes", F_OK) == 0);
int fast = scopes_present ? manifest_load_records(core) : -1;   // 有 scopes 就走快速路径
if (fast > 0) { LOGI("Manifest fast path: %d plugins (no scan)", fast); }
else          { nyako_scan_all_plugins(core); nyako_write_manifest_json(core); ... }
```

而 `manifest_load_records()` 的"新鲜度"校验只针对**清单里已记录的文件**：
外部插件比对 `so_size`/`so_mtime`（`:1873-1882`），内置插件比对 `/system/lib64` 的文件集合（`:1900-1914`）。
**没有任何"发现新 .so"的逻辑** —— 新放进来的模块对快速路径是隐形的，于是：

- 文件拷进去了 ✅、SystemUI 重启了 ✅、插件**没被 dlopen** ❌ → 没有 hook → 还是不播动画。

框架自己的文档 `AGENTS.md` §9 写得很明确：

> **手动部署新的/更新的外部插件 .so（adb/root）**：还要 `rm /data/local/nyako/state/manifest.json /data/local/nyako/state/scopes`，
> 否则作用域门禁会一直用旧的声明列表，永远不会发现新插件。

正确顺序（`fpanim_install.sh` 已修正为这样）：

```sh
adb shell su -c "rm -f /data/local/nyako/state/manifest.json /data/local/nyako/state/scopes"
adb shell su -c "killall com.android.systemui"
sleep 8
adb shell su -c "logcat -d | grep -aE 'Scanned|Manifest fast path|installed slot|NyakoRuntime' | tail -20"
```

判据要用**真实存在的**日志行（本 ROM 的日志里**没有** `installed slot=` 这种行——早期给的这条验证建议是错的）：

```
Nyako: Manifest fast path: 5 plugins (no scan)          # 首次重建时是 "Scanned N plugins"
Nyako: plugin 'FOD Unlock Animation' scope='systemui' LOADED
Nyako: Scope loading complete: N plugins loaded for 'com.android.systemui'
```

真正判定「hook 被走到」的是这一行（dispatcher 在**第一次**经过某个 slot 时打一次）：

```
NyakoRuntime: first callback slot=2 public final boolean com.android.systemui.biometrics.UdfpsController.onTouch(long,android.view.MotionEvent)
```

（用管理器安装时管理器会替你删缓存；但它不一定顺手重启 SystemUI，所以要自己重启。）

### 5.2 第二次「装了还是不动」的原因：ART 内联让 hook 静默失效（实测）

`1.txt`（10-08 22:36–22:37）里，**插件已经加载进 SystemUI**（`NyakoFpAnim: finger up (aod synthetic) …` 打出来了），
同一段里真实触摸 **5 次**（HAL `QFP: onPointerDown` ×5，它唯一的调用者就是 `UdfpsController#onFingerDown`），
但 `onFingerDown` 的 hook **一次都没进**——`first callback slot=` 只出现过 `slot=1`（AOD 合成抬手）。

先排除了签名问题：用设备自己的 `classes2.dex` 逐字核对过

```
UdfpsController: onFingerDown (JIFFFFFJJZ)V        PUBLIC FINAL   reg=30
UdfpsController: onFingerUp   (JLandroid/view/View;IFFFFFJJZ)V  PUBLIC FINAL  reg=33
UdfpsController: onTouch      (JLandroid/view/MotionEvent;)Z   PUBLIC FINAL  reg=32
UdfpsController: onAodInterrupt (IIFF)V            PUBLIC        reg=21
```

规则串 `(Ljava/lang/Object;JIFFFFFJJZ)V` 与 `RuleInstaller.match()` 的匹配条件（hook 名 = 规则名、
`descriptor(hook)` = 规则串、`hp.length == params.length + 1`、`hp[0] == Object.class`、参数/返回类型逐项相等）**完全吻合**。

真正的原因是 **ART 把调用点内联了**：`onTouch` 内部对 `onFingerDown/onFingerUp` 的调用被 AOT 编译时内联进 `onTouch`，
而引擎（LSPlant）替换的是**方法入口**——内联进去的副本根本不走入口，hook 静默失效。

> 判别特征：**同一个方法、不同调用点表现不同**。11 参 `onFingerUp` 被 AOD 路径（`tryAodSendFingerUp` 的 Runnable，
> 属于**另一个类**）调用时 hook 正常命中；被同类 `onTouch` 调用时不命中。
> LSPlant 换入口时会对**目标方法** deoptimize，但不会自动 deopt「把目标内联进去的调用者」；
> 框架自己只在 bootstrap hook 上显式用 `deoptCallers()`（`RuntimeBootstrap`）处理这件事，插件规则没有这一步。

**修法**：把触发点挪到**调用方来自别的类**的方法上（这类调用点不会被内联掉）。v2 的 4 条规则：

| slot | 目标 | 触发时机 | 调用方（dex 核对） | 本机是否命中 |
|---|---|---|---|---|
| 0 | `onFingerDown(JIFFFFFJJZ)V` | 按下 | 同类 `onTouch` | ❌（被内联） |
| 1 | `onFingerUp(JLandroid/view/View;IFFFFFJJZ)V` | 抬手 | 另一类的 Runnable（AOD 合成抬手） | ✅（AOD）/ ❌（同类 `onTouch`） |
| **2** | **`onTouch(JLandroid/view/MotionEvent;)Z`** | **屏亮：DOWN 起播 / UP·CANCEL 停** | `UdfpsController` 内部 `View.OnTouchListener`（另一个类） | ✅ 主触发 |
| **3** | **`onAodInterrupt(IIFF)V`** | **息屏 AOD 按下** | `AuthController#onAodInterrupt` | ✅ |

`onTouch` 的 hook 读 `MotionEvent.getActionMasked()` 决定起播/停播，**原方法照常执行并透传其 `boolean` 返回值**；
`onAodInterrupt` 同理（`AuthController.java:565` → `UdfpsController.java:811`）。

## 7. 边界与已知事项

- `FlymeFpAuthAnimView` 在**构造时**读一次 `fingerprint_animation`（`loadAnimationType()`），所以改设置后要**重启 SystemUI / 息屏再亮屏**才换动画——这是 Flyme 自身行为，不是本模块的问题。
- SVGA 是**异步解码**的（`decodeFromAssets` 的 `onComplete` 才 `setVideoItem`）；开机后第一次触摸若解码未完成可能不出画面，之后正常。
- 动画时长跟随手指按住时间（与 Meizu 原行为一致：抬手即停）。
- 只影响锁屏/AOD 的 FOD 动画；不动认证逻辑，也不动图标尺寸（那是另一个模块 `fodsize`）。
